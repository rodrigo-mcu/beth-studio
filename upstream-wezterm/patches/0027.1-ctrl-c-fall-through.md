# Patch 0027.1 — Ctrl+C in a shell aborts the process (fall-through when no selection)

**Applied:** 2026-06-07
**Files:**
- `upstream-wezterm/wezterm-gui/src/termwindow/mod.rs`

**Status:** Active

## What

The `CopyTo` branch in `TermWindow::perform_key_assignment` now
returns `PerformAssignmentResult::Unhandled` when the current
selection is empty. The upstream `process_key` fall-through (in
`wezterm-gui/src/termwindow/keyevent.rs:328-425`) then sends the
keypress to the pane, which delivers ETX (0x03) to the shell and
aborts the running process.

When there **is** a selection, the binding behaves exactly as before
— the selected text is copied to the clipboard (and the primary
selection, for Linux/X11).

## Why

Patch 0021 added three default `Ctrl+`-modifier bindings for
Windows/Linux to fix the broken `Ctrl+C` / `Ctrl+V` / `Ctrl+Insert`
defaults upstream:

```rust
// Ctrl+C → CopyTo(ClipboardAndPrimarySelection)
result.push((
    Modifiers::CTRL,
    KeyCode::Char('c'),
    KeyAssignment::CopyTo(
        config::keyassignment::ClipboardCopyDestination::ClipboardAndPrimarySelection,
    ),
));
```

The upstream `CopyTo` handler at
`wezterm-gui/src/termwindow/mod.rs:2866` was:

```rust
CopyTo(dest) => {
    let text = self.selection_text(pane);
    self.copy_to_clipboard(*dest, text);
}
```

It always called `copy_to_clipboard` and returned `Handled`. When
the user pressed `Ctrl+C` in a shell **without a selection**, the
handler copied an empty string and consumed the keystroke — so the
shell never saw the ETX byte and the running process could not be
aborted with `Ctrl+C`. The user reported:

> "CTRL+C tem que abortar o processo e não está funcionando"

The fix matches the behaviour of every other terminal that exposes
both copy-on-Ctrl+C and shell-Ctrl+C (Windows Terminal, ConEmu,
iTerm2, GNOME Terminal, …): `Ctrl+C` is *both* the copy keystroke
and the abort keystroke, and the chosen action depends on whether
the user has a selection.

## Revert

1. In `wezterm-gui/src/termwindow/mod.rs`, change the `CopyTo(dest)`
   branch back to its 2-line upstream form (always call
   `copy_to_clipboard` and return `()` — the implicit `Handled`).
2. Remove this file and the row for patch 0027.1 from `PATCHES.md`.

## Risk

Low. The branch only diverges from upstream behaviour in the
"Ctrl+C with empty selection" case, which is exactly the case the
user reports broken. The "Ctrl+C with selection" case is unchanged.
Users who want the old "always copy, never pass through" behaviour
can override the binding in their `wezterm.lua` `config.keys` table
— the user config still wins because `default_key_assignments` is
merged before the user table.
